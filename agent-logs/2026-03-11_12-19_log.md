## Full Pipeline Summary

### 1. README.md

Already shown above in full. The README covers the CLI, generated API patterns (constructors, inheritance, handles, collections, enums, etc.), architecture, and known issues.

### 2. Config/TOML Parsing ([config.rs](crates/opencascade-binding-generator/src/config.rs))

The `BindingConfig` struct deserializes [bindings.toml](crates/opencascade-sys/bindings.toml):

```rust
pub struct BindingConfig {
    pub modules: Vec<String>,              // OCCT modules (glob patterns)
    pub exclude_modules: Vec<String>,      // Modules to skip
    pub exclude_headers: Vec<String>,      // Individual headers to skip
    pub include_headers: Vec<String>,      // Extra individual headers
    pub exclude_methods: Vec<String>,      // "ClassName::MethodName" to skip
    pub ambiguous_methods: Vec<String>,    // Known overload conflicts
    pub non_allocatable_classes: Vec<String>, // No constructors/destructors
    pub manual_types: HashMap<String, ManualType>,  // Opaque types from manual/ files
    pub template_instantiations: HashMap<String, TemplateInstantiation>, // Template aliases
    pub occt_alias_type_overrides: HashMap<String, String>, // Canonical→public name rewrites
    pub void_pointer_types: Vec<String>,   // Map to *mut c_void
    pub split: SplitConfig,               // Toolkit-level splitting for parallel builds
}
```

`load_config()` reads the TOML, `expand_headers()` resolves module globs against the OCCT include directory.

### 3. Two-Pass Pipeline

1. **Parse** ([parser.rs](crates/opencascade-binding-generator/src/parser.rs)): libclang parses C++ headers → `ParsedClass`, `Method`, `Constructor`, etc. ([model.rs](crates/opencascade-binding-generator/src/model.rs))

2. **Resolve** ([resolver.rs](crates/opencascade-binding-generator/src/resolver.rs)): Builds a `SymbolTable` — applies all filters, computes names, determines `BindingStatus` (Included/Excluded with reason)

3. **Generate** ([codegen/](crates/opencascade-binding-generator/src/codegen/mod.rs)):
   - [bindings.rs](crates/opencascade-binding-generator/src/codegen/bindings.rs): Computes `ClassBindings` IR (all naming, overload suffixes, conflict resolution done once)
   - [rust.rs](crates/opencascade-binding-generator/src/codegen/rust.rs): Emits `ffi_types.rs` (type declarations), `ffi_extern_*.rs` (extern "C" blocks), and per-module re-export `.rs` files
   - [cpp.rs](crates/opencascade-binding-generator/src/codegen/cpp.rs): Emits `wrappers*.cpp` C++ wrapper functions

### 4. How Types Are Declared (No CXX Bridge!)

This is **not** a CXX bridge. It's a pure `extern "C"` FFI. Types are declared as opaque `#[repr(C)]` structs:

```rust
// In ffi_types.rs (generated by rust.rs line 209-210):
#[repr(C)]
pub struct STEPControl_Reader { _opaque: [u8; 0] }
#[repr(C)]
pub struct STEPControl_Writer { _opaque: [u8; 0] }
```

Per-module re-export files alias and add impls:

```rust
// In step_control.rs:
pub use crate::ffi_types::STEPControl_Reader as Reader;

unsafe impl crate::CppDeletable for Reader {
    unsafe fn cpp_delete(ptr: *mut Self) {
        crate::ffi_extern_TKDESTEP::STEPControl_Reader_destructor(ptr);
    }
}
```

### 5. Send/Sync Mechanism

**There is no generated `Send`/`Sync` implementation for any type.** Here's how it works:

- **Opaque types** (e.g., `STEPControl_Reader`) are `#[repr(C)]` structs with `_opaque: [u8; 0]`. Being extern types with no Rust-side `Send`/`Sync` impl, they are **neither `Send` nor `Sync`** by default. (Opaque `#[repr(C)]` types are `!Send + !Sync` because Rust can't verify thread-safety.)

- **`OwnedPtr<T>`** ([owned_ptr.rs](crates/opencascade-sys/src/owned_ptr.rs#L130-L133)) conditionally implements `Send`/`Sync`:
  ```rust
  unsafe impl<T: CppDeletable + Send> Send for OwnedPtr<T> {}
  unsafe impl<T: CppDeletable + Sync> Sync for OwnedPtr<T> {}
  ```
  Since the underlying opaque types don't implement `Send`/`Sync`, `OwnedPtr<STEPControl_Reader>` is also `!Send + !Sync`.

- **The binding generator never emits `unsafe impl Send/Sync`** for any type. It only emits:
  - `unsafe impl CppDeletable` (for destructor)
  - `unsafe impl CppCopyable` (for clone/copy where applicable)

- **There's no `bindings.toml` config** for marking types as `Send`/`Sync`. If you wanted to make specific types thread-safe, you'd need to either:
  1. Add manual `unsafe impl Send for SomeType {}` in a `manual/*.rs` file
  2. Add a new config option (e.g., `send_sync_types`) to the binding generator and have it emit the impls

### 6. Generated step_control Reader/Writer

The generated [step_control.rs](crates/opencascade-sys/generated/step_control.rs) contains:

## Implementation Details

The generated code has two layers: a `pub(crate)` FFI module containing the raw extern "C" bindings, and public per-module re-export files that provide the user-facing API.

### Internal: `ffi.rs` (the FFI declarations)

A single `extern "C"` block declares all types and functions using full C++ names. This is `pub(crate)` — users never interact with it directly.

Types use their full C++ identifiers as Rust names to avoid collisions:

```rust
// generated/ffi.rs (pub(crate), not user-facing)
extern "C" {
    // Opaque C++ types -- full C++ names
    pub fn gp_Pnt_ctor_real3(theXp: f64, theYp: f64, theZp: f64) -> *mut gp_Pnt;
    pub fn gp_Pnt_destructor(self_: *mut gp_Pnt);
    pub fn gp_Pnt_x(self_: *const gp_Pnt) -> f64;
    pub fn gp_Pnt_set_x(self_: *mut gp_Pnt, theX: f64);
    pub fn gp_Pnt_distance(self_: *const gp_Pnt, theOther: *const gp_Pnt) -> f64;
    pub fn gp_Pnt_mirrored_pnt(self_: *const gp_Pnt, theP: *const gp_Pnt) -> *mut gp_Pnt;
    // ... thousands more
}
```

All methods go through extern "C" C++ wrapper functions. There is no ABI-level distinction between "direct" and "wrapped" methods — everything is wrapped for uniform handling.
